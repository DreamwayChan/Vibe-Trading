## 复权因子回补（P3 收尾，同日）

**Tushare `adj_factor` 走不通（实测）**：本机三个 token 都是 `1次/小时`，调用即报
`40203 频率超限(1次/小时)`。按交易日取 1,212 次 = 50 天，按标的 5,576 次更久。
教训：接口能否批量要按**账号档位**实测，不能按文档「一次一个交易日」推断。
日线 Tushare 路径里的 `_attach_adj_factor` 在当前档位下从未生效。

**改走 baostock**：`query_adjust_factor(code, start, end)` 一次给该标的全部除权事件，
~0.16s/标的、免 token、本地 socket。`backAdjustFactor` = 累计后复权因子（单调、上市起算），
语义等同 Tushare `adj_factor`。因子是**阶梯函数**（每股每年 1–2 个台阶），所以修复是
「一标的一次调用 + searchsorted 展开」，不是「一交易日一次调用」。

**落点实测**：因子从**除权日当天**起生效。600519.SH 2026-06-26：原始 -3.59%（含分红除权）
→ 复权 -1.30%，序列连续。推到除权日之后生效会凭空多 2.3% 假涨。

**实现**：`bars.daily(mode="adj_factor")` → `_repair_adj_factor`；按 600 标的分块，
每块每年分区各读一次（`symbol IN (...) AND date BETWEEN`），整行写回（三列 frame 会把
OHLC 覆盖成 null）。判据「仍有任意一行 null」而非「跑过没有」，失败标的保持原值。
北交所 baostock 不认（`920xxx`），354 个标的保持空值并记 note。CLI：`--mode adj_factor`。

**复权视图单点**：`hub.adjusted_bars(mode="qfq"|"hfq")` + `hub.bars(adjust=)` + 私有
`_rebase_on_factor`（唯一算术）。qfq 按可见区间最后一根归一；`volume/amount` 不缩放；
`pct_chg` 用复权 close 重算（库里是不复权口径，除权日会把分红记成亏损）；无因子行剔除并
计数进 `attrs["missing_factor"]` / 信封 warnings。`/data/bars?adjust=qfq`。

**顺手修掉**：`scripts/ingest.py` 原来不读 `agent/.env`（服务端读），导致手工跑就「没配
token」——恰是运维修数据的时候。现在启动即 `load_dotenv`，真实环境变量优先。
baostock 的 `login success!` 打到 stdout 会污染 `--json`，用 `_quiet_stdout()` 吞掉。

**前端**：MarketPanel 加「不复权/前复权/后复权」分段控件（仅 1d 显示），5 语言文案，
取值走 `/data/bars?adjust=`，不在前端算复权。

**实测**：5,965,635 行 / 1,212 交易日 / 5,222 标的 / 1,324s（约 22 分钟），覆盖率 95.76%；
重跑 2 秒返回「无需修复」。校验：行数与 close/volume/source 计数未变；601398.SH 五个除权日
原始 -5.85%~-6.16% → 复权后约 0%；复权未制造新的极端单日收益。扫出 1 个源站瑕疵：
000002.SZ 2025-01-09 因子 -1.18% 而股价 -0.14%（源站阶梯不单调），修复不改写、只报
「N 个标的因子回退」。

**测试**：后端 179 passed（ingest 31 / hub 27，新增因子阶梯、除权日落点、部分覆盖重取、
取数失败保留原值、因子回退告警、北交所留空等用例）；前端 6 passed；`tsc -b` 干净。

**仍遗留**：amount 全空（腾讯/新浪不给，Tushare `daily` 同档位限制）、北交所无因子、
前复权基准随窗口滑动（跨窗口比价用 hfq）、分钟线无因子。

## P4 任务层：sqlite 账本 / 断点 / 取消（同日）

**为什么做**：分钟线全市场一场 = 5,500 次串行取数 ≈ 18 分钟 > UI 任务 600s 预算，而旧
`intraday()` 把 frame 全攒内存、末尾写一次 → 每次都在同一位置被砍、尾巴永远补不到，是活锁。
日线/复权之所以能"> 重跑即续跑"，是因为湖本身是断点（按标的跨度判覆盖）。

**账本**：`_ingest/jobs.json` → `_ingest/_jobs.sqlite`（stdlib sqlite3，WAL）。旧文件首次
打开时导入一次（running→failed）。列含 `cursor / owner / heartbeat_at / cancel_requested`。
`claim()` 用 `BEGIN IMMEDIATE` 做跨进程单飞（原来 `_active` 只在进程内）。
**租约不用 pid**（Windows 上 `os.kill(pid,0)` 不是探针）：运行时 15s 心跳，120s 无心跳则回收。

**游标**：`ingest.checkpoint(cursor)` 在**写盘之后**调用并立即持久化。只有 failed/cancelled
的任务把游标交给下一次运行（done 不交，否则每日"补齐"会跳过当天）。游标是提示，湖是事实。

**取消**：协作式，ingester 在单元边界查 `cancelled()`，drain 在途 + flush + 写游标，状态
`cancelled`。心跳线程把账本里的 `cancel_requested` 镜像成进程内 Event（跨进程取消）。API
`POST /data/ingest/jobs/{id}/cancel`；CLI `--cancel/--jobs`；控制台任务行加「取消」+「已完成 x/y」。

**分钟线三处修复**（缺一不可）：① 按 400 标的分块写；② 覆盖判据从"数据集水位线"改为
逐标的 `_intraday_covered`（旧判据是任意一个标的有数据就整体"已入库"，活锁的另一半）；
③ `AsOf.date` 是 str，旧代码调 `.isoformat()`，**第一次真实调用就崩**，此前无端到端用例。

**真实数据事故**：验证 `--refresh` 时把三只票 41 天的 `adj_factor` 抹没了 —— `_upsert_file`
是"现有+新行 dedupe keep=last"，整行替换，源不给因子就写成 null。修在湖层：
`_carry_over_nulls` 合并前用同 key 旧行补 incoming 的空值 → 契约变为「null 不覆盖已有值」。
已用 baostock 重跑恢复，并确认再次刷新后 44/44 行仍有因子。

**实测**：`bars_intraday --limit 8` → 3 个新取/5 个跳过、864 行，断点
`{"session":"2026-11-02","done":3,"total":3}`；再跑 0 次请求。
后端 198 passed（ingest 41 例），前端 98+1 passed，`tsc -b` 干净。

**下一步**：分钟线五年回补本身（按交易日循环 + baostock `query_history_k_data_plus` 支持
5/15/30/60 分钟区间）；退市股；任务队列优先级；amount 仍空。

**补记两个坑（同日晚）**：
1. 账本连接必须**按任务钉死**（`_RunContext.ledger`）。最初每次按当前湖根重解析，后台心跳
   线程在环境变化后把记录写进了另一个库，真湖里留下一条幽灵任务（测试切 env 时真的发生了）。
2. `EnvConfig` 是缓存单例，且**优先级高于** `VIBE_TRADING_LAKE_ROOT`（`lake_root()` 先读
   config 再读 env）。测试 fixture 里 setenv 后必须 `reset_env_config()`，否则湖根被上一个
   用例钉住，后台线程甚至会写进开发者的真实湖。

## P5：分钟线区间回补（2026-11-02 晚）

**源选型（实测）**：腾讯 mkline 320 根滚动；东财 klt=5 只有 1,536 根≈32 天（lmt 给 100 万
也一样）；Tushare stk_mins 有权限但**1 次/小时**，等于不可用；只有 **baostock
`query_history_k_data_plus`** 能按区间取，最早 2019-01-02，含 amount，约 700–830 行/秒。
→ `intraday(start=)` 分发到 baostock 区间路径；无 start 仍走腾讯补当天。

**实现**：工作单元＝一个标的×整段区间（按行计费源，5 年一次往返 ≈ 58k 行）；
写放大靠缓冲（400 万行 flush 一次）压到每分区重写 ~70 次而非 5,000 次；
`_intraday_year_counts` 一次 duckdb 聚合拿每 (symbol,year) 已存 session 数；
`_ingest/intraday_attempts.json` 记住「问过但没数据」的 (symbol,year)，否则 2024 上市
的票每次都被重取 2019–2023；attempts 只在收到回复后记账，失败/超时的不记。

**口径**：volume 股→手（÷100），amount 元直接存（`bars_intraday` 新增该列），价格不复权；
分钟线不存 adj_factor（读取时按日复算）。

**踩坑（重要）**：验证时用裸 duckdb 读 `date=2025-03-31/data.parquet`，DuckDB 默认开启
hive 推断，**用分区常量覆盖了真实 date 列**（类型降成 DATE），48 根 bar 全变 00:00、排序
失效，一度误判成「分钟线是前复权」。实为读法错误——`lake.read_parquet_file` 的
`hive_partitioning=false` 是正确性要求，不是优化。加 `hive_partitioning=false` 后
09:35 open 1580.98、15:00 close 1561.00 与日线完全一致。
教训：验证必须换一个独立口径对照（拿日线开收盘价比），不能只看行数/量对得上。

**成本账**：全市场五年 ≈ 2.9 亿行/10GB/单连接 80–110 小时 → 不该一次做。建议研究池
（几百只）×五年先做，全市场靠每日窗口累积。CLI 已支持 `--start/--end/--limit`，
断点续跑+覆盖检查就位。

测试：`test_data_ingest.py` 51 passed（新增 10）；`test_data_hub.py` 27 passed。
文档：`docs/design/data-center.md` §19。

**分钟线复权（同轮补齐）**：原先 `adjusted_bars("5m")` 直接抛「该周期没有复权因子」。
现在 `_attach_daily_factor` 按 symbol 对 session 做 `merge_asof(backward)` 把日线因子挂到
分钟 bar 上（向前多取 365 天日线，覆盖停牌/长假），再走同一个 `_rebase_on_factor`；
`bars()` 与 `adjusted_bars()` 两个入口都挂。查不到更早因子的仍剔除并计 `missing_factor`。
测试：hub 30 passed（+3：跨除权 qfq、hfq、无当日日线时回退前值）。

**实测（真实入库）**：30 标的 × 2025 全年 5m → 349,920 行 / 243 交易日 / 634 秒
（552 行/秒，0 失败）；重跑 3.1 秒「均已在湖内，无需重取」；1h × 1 标的 × 1 月 → 84 行。
数据校验：000001.SZ 2025-06-30 分钟 48 根 open/close = 12.14/12.07 与日线一致，
volume 1,504,820 手 vs 日线 1,504,819.65 手。

**又抓到一个 bug**：attempts 键原来只有 `SYMBOL|year`，5m 跑过之后 1h 直接报「已完成」
（实测 0 行 0 请求）。改为 `interval|SYMBOL|year`，旧格式读取时补 `5m|`。两条测试锁住。
另修 `_bs_minute_freq` 的键：`normalize_interval("60m")` 返回 `1H`（大写），原来映射不到。

测试最终：数据层 99 passed（ingest 53 + hub 30 + catalog/cli/routing 16）。

## P6：可靠性补洞 + 前端回补入口（2026-11-02 深夜）

**三件事一起做**：卡死、孤儿任务、前端只能补当天。

**① 卡死（最危险）**：baostock `send_msg` 的 `while True: recv()` 没有 `b""` 判断，
对端关闭 → 忙等满核永不返回；心跳是独立线程，只证进程活着不证取数在推进 → 租约永远
新鲜 → 任务永远 running。**socket settimeout 试过不能用**：一年请求要 14–21 秒，
`settimeout(5)` 后正常请求 5.9 秒报 10002007（误杀）。改用 watchdog 线程到点
`shutdown(SHUT_RDWR)+close`，实测 3 秒内打破阻塞。预算 `QUERY_BUDGET_S=180`（5 年
70–90 秒的 2 倍余量）。

三个坑：a) 断连后 baostock 先抛 10002007 → 走不到 tripped → `_connected` 仍 True →
下一次调用 0.00s 立刻失败（用废 socket）；修：except 里也查 tripped。b) 断连时
baostock 往 stdout print 中文错误 → 污染 `--json`；修：call 包 `_quiet_stdout`。
c) **被 drop 的查询返回 error_code 0 + 截断分页**（实测 rows=2000），守卫触发后必须抛，
返回那个 frame 会把半年 bar 当成功写进湖。

**② 孤儿任务**：`_expire_inner` 原来只在 `claim()` 跑，被 kill 的 job 要等下次提交
同数据集才被回收 → 控制台永远转圈。改成 `live()` 先 `expire_stale()` 再读（异常吞掉，
读接口不该因一次写失败 500）。

**③ 前端区间回补**：新增 `components/data/IngestForm.tsx`，**字段由 `option.params`
（后端 inspect.signature）推导**，不硬编码数据集名。两个入口分开：表头按钮 `{dataset}`
= 按水位补缺口；展开表单 = 显式窗口。空日期框不发（否则 `start=""` 会被读成空窗口）；
反序窗口前端拦住（「取不到」和「已覆盖」结果长得一样）。5 语言 +13 键（dataCenter 112→125）。

**端到端实测**：TestClient 打 POST /data/ingest（临时湖）→ 202 → params 正确 →
done rows=48/1 session/1 symbol/source=baostock。

**测试**：ingest 58（+5，含清理 7 个重复定义的函数——之前「56 passed」一直在少跑）、
IngestForm 9（新）、DataCenter 6（+1）；后端数据层 104 passed；前端 399/3（3 个
ja/ko/ar 的 capitalFlow/process 旧账）；tsc 干净。文档 §20。

**核实到两个和假设不符的事实**：日线只有 2021-11-01 起（622.9 万行/1,212 日/5,576 标的），
不是五年以上；退市股 **0 覆盖**（每年在册只增不减 4489→5576，「2021 有 2025 无」= 0）。
生存者偏差是实证，不是理论风险。
