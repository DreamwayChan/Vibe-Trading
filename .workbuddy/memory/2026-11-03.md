## 市场优选改为读数据中心（湖）取数
- 问题：`market_pick` 走 `_fetch_universe_ohlcv → fetch_data_map → tushare`，即使数据中心刚入库最新日 K 也会重拉 400 天全市场（约 230 次 `daily()`）；loader 缓存 key 含 (start,end)，跨交易日必 miss。
- 方案：新增 `src/data/hub.py::bars_frame` + `StoredBars`（按标的原始 OHLCV 帧 + 每个标的最新 source，不走 `bars()` 的两位小数/JSON 封装）。
- `_default_fetch` 改为湖优先三分支：整窗覆盖→直接用；只缺尾部且湖 source 与网络 source 一致→只补 `[last+1, end]` 并 concat；湖历史起点晚于窗口+7 天宽限或 source 不一致→整窗重拉。尾巴探测用 CSI300 单次调用，避免节假日把几千只票的缺口扇出。
- 关键取舍：头 7 天宽限（400 天窗口本就是 padding）；跨源不拼接（复权口径可能不同，接缝会造出一根假收益）；`hub.bars_frame` 复用了 loader 边界的 `validate_ohlc`。
- 测试：`tests/test_market_pick.py` 新增 8 例（全覆盖零网络 / 尾缺口只拉一天 / 节假日探测 / 历史过短整拉 / 跨源不拼 / 停牌不算错误 / 空湖回退），`tests/test_data_hub.py` 新增 3 例。
- 备注：`tests/test_lake_migrate.py::test_migration_backfills_provenance` 因 bars schema 多了 `amount` 列而失败，属既有问题（fixture 未更新），与本次改动无关；`test_data_ingest.py::test_single_flight_rejects_a_second_job` 全量跑时偶发超时，单独跑通过。

## 自检：首轮湖优先取数的三个 bug + 一处性能修正
- **bug1 标签说谎**：`FetchStats.label()` 旧判定 `tail_spliced==0 → lake`，于是「4599 只来自湖 + 1 只新股整窗拉」报 `lake`。改为按 `network_calls`（只统计按标的的行情请求）判定；CSI300 探测单记 `probes`，不算 network（它不产出 K 线）。
- **bug2 停牌扇出**：补尾按 `(gap_start, end, source)` 分组，长期停牌票各自最后一根不同 → 每票一桶一请求。实测 30 只停牌 = 30 次单票调用。修复：以 `_market_latest`（最后交易日的**众数**）为基准，落后 > `STALE_TAIL_DAYS`(30 天) 直接沿用湖帧（`stale_kept`）。取众数而非 max：max 会被一条未来日期脏数据带偏；整湖滞后时众数一起滞后 → 无人被跳过 → 全量补尾（正确语义）。实测 4600 只含 100 只停牌：调用数 101 → 2（1 探测 + 1 批量补尾）。
- **bug3 异常打穿**：补尾/整拉直接抛给调用方，一次 vendor 500 会让本可全本地完成的扫描整体失败。新增 `_pull()` 统一包 try/except → 逐标的错误 + 保留湖帧。同时 `_market_traded_in_gap` 只在**成功返回空**时判「休市」，token 过期/500 一律 fail-open 去补尾。
- **性能**：`validate_ohlc` 从「每票一次」移到 `hub.bars_frame` 对长表一次向量化（行级不变量，与标的相关性为零）。4600 只 × 349 根真实 parquet：read_lake 8.7s → 4.8s（1.0s parquet + 3.3s 分帧为下限）。
- 前端：未知 `bars_source` 不再兜底显示「外部接口」，直接不渲染（徽标存在的意义就是不猜）。
- 回归：相关 9 个文件 301 passed；test_data_lake_fetch 13 例、test_data_hub 34 例。全量 125 failed 全是环境旧账（mcp 版本不匹配 ImportError、Windows 符号链接 WinError 1314、网络 loader），与本次无关。
- 文档：data-center.md §21.3 重写标签语义、§21.4 补测试清单、新增 §21.6 记录这三处；CHANGELOG Fixed 段同步。
